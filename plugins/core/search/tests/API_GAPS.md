# API gaps of the Workspace search feature tests

Items missing from the skeleton, and wire formats no manual page names. Every one is used in the
tests as written below; the gap helpers in `tests/features/support.rs` hold the wire-format ones.

- `ilium-plugin-testkit`: `FakeTree::set_screen(&mut self, id: u64, text: &str)`; the text `terminal.read-screen` returns for pane `id` (F-009, used by `add_terminal`).
- `ilium-plugin-testkit`: `FakeHost::vector(&mut self) -> &mut FakeVector` with `embed_batch_sizes(&self) -> Vec<usize>`, `top_k_requests(&self) -> Vec<u32>` and `set_top_k(&mut self, Vec<(String, f32)>)`; fake of the vector API and `inference.embed` (F-009, search by meaning, 256-text batches, top 20).
- `ilium-plugin-testkit`: `FakeHost::extensions(&mut self) -> &mut FakeExtensions` with `on_run_hook(&mut self, point: &str, reply: HookReply)`, `hook_calls(&self, point: &str) -> Vec<String>` (payload JSON), `contribute_collect(&mut self, point: &str, id: &str, priority: i32, entry: serde_json::Value)`, `set_service_reply(&mut self, service: &str, reply: serde_json::Value)` and `fail_service(&mut self, service: &str)`; fake of an extension-point owner's host side (F-009, `rank` and `sources`).
- `ilium-plugin-core-search`: `impl ServiceProvider for SearchServer` (service `ilium.core.search/query`, reply `Done` JSON `{ "hits": [...] }`) and the `service-provider` export in `manifest.json` plus `services.provide:ilium.core.search/query`. The page lists the service and the extension points but the exact manifest (COR-050) declares neither the export nor the provide grants; the manifest tests assert the page as printed.
- `ilium-plugin-core-search`: the server handles `Event::Message` on channel `ilium.core.search/query` (payload JSON `{ "revision": u64, "query": String }`) and answers the sending client with a `message` intent on `ilium.core.search/results` (`{ "revision", "hits": [ { "id", "kind": agent|terminal|file|meaning|<source kind>, "title", "score"?, "before"?, "matched"?, "after"?, "line"?, "last_command"?, "pane"? } ] }`). Documentation gap: no page names the channel or the payload between the two sides. The client sends the query message on `filter-changed` with a revision starting at 1 and counting up per new text.
- Documentation gap: the page says the kernel debounces `filter-changed` to 150 ms, while src/docs/panes-and-layout.md ("Workspace search", about one second) and the original `SEARCH_DEBOUNCE` (1 s) say one second. The ported debounce tests assert the page value.
- Documentation gap: `terminal.read-screen` reads the visible screen only; the original searches the retained terminal history and jumps to a raw byte offset (`history_end_byte`). The ported terminal tests cover the screen text; the offset and history are not testable against the page.
- Documentation gap: the page names no intent for jumping to a hit (focus a pane, scroll a terminal, open an editor at a line). The tests assert only the documented `close-view` with correlation 2.
- Documentation gap: the original caps results at 800, keeps 72 context characters and skips captures over 8 MiB; the page states none of these. The tests keep the original values (parity, COR-011).
- `ilium-plugin-core-search`: `impl HookHandler` is not needed (the plugin owns `rank` and runs the hook); no gap.
- `ilium-plugin-sdk` testing `FakeHost::jobs().list()` is assumed to keep finished jobs listed or drop them; the tests only count jobs after a new query, never rely on either.
- G8: `ViewHost::set_text(key: &str, text: &str)` and a scroll read-back for a `%list` -- needed by the panel's query input (`results::SearchState::query` is edited by the host widget, not by the plugin) and by the result list's scrollbar (`results::result_at_row` expects the scroll offset).
- G10: `fs.read:project` (read an open file's text) and `jobs.run` (`scan-files`) -- needed by `matching::search_workspace`, the pure scan that a `scan-files` job runs over the `Source` snapshots; the sources themselves (terminal retained history, editor buffers, board cards) have no import yet.
- G17: a server seam that returns a terminal's retained raw history bytes (`Content::Terminal`) and the jump offset (`Location::Terminal { history_end_byte }`) -- needed by the terminal source of `matching::search_workspace`; `terminal.read-screen` returns only the visible screen.
- Pure rule modules `src/matching.rs` (control stripping, case-insensitive match, context, last command, result cap 800) and `src/results.rs` (debounced `SearchState` on a millisecond clock, 1 s `SEARCH_DEBOUNCE_MILLIS`, continuation queue of 32, 5-row result geometry) are ported from ilium-client/src/search_ui.rs; the command and panel wiring waits on the gaps above.

## Move blockers (verified 2026-11-14)

The `search` kernel files stay PORT-KEEP after the gap streams. The list below is the exact reason per file; the cuts file `docs/tasks/02-cuts/search.md` carries the key table.

- `ilium-client/src/search_ui.rs`: the dialog has a text input and a scrolling result list, K3. `Mode::Search` is matched in `app.rs` (12), `keys.rs` (10), `mouse.rs` (8), `control/executor.rs` (8), `ui.rs` (4), `control/snapshot.rs` (3), `control/mod.rs` and `resource_queue/action_tests.rs`; every one needs a hunk once a plugin route exists, and `ilium ctl` search operations (executor, snapshot) read the same state (K4).
- `ilium-client/src/search_workers.rs`: the kernel searches the in-memory workspace (tree titles, whole terminal scrollback bytes, editor and board text) and the semantic index, not files on disk. A plugin sees the tree through `tree` and only the visible screen through `terminal.read-screen`. Wanted: an import that returns a pane's full scrollback text, and `inference.embed` backed by a provider (`InferenceImport` is a skeleton, K5).
- The `f` key, the context-menu `Search` arm and the tree toolbar `Search` button stay kernel until the dialog is a popup that accepts text input (K3). The manifest chord is already `f`.

Blocker keys (verified against the tree on 2026-11-14; each names the exact missing piece):

- K1 intents. `ilium-server/src/plugin_host/facade.rs` `apply_intent` routes only RenameNode, MoveNode, CloseNode, SetNodeLocked, CreatePane, ResizePane, CreateGroup, CreateSplit, SetBookmarked, SetExpanded, Message, SetStatusSegment, ClearStatusSegment, SetDecoration, ClearDecoration, SignalPane, OpenView and CloseView. Every other arm ends in `unsupported("this intent")`: `Intent::SendInput` (needs `Delivery::{Typed, Submitted, Pasted}` plus `stages` / `prompt_epoch` mapped to the server requests `UserKeyInput`, `SubmitTerminalText`, `PasteTerminalText`, `SchedulePaneInput`), `EditorOpen`, `ApplyEdits`, `Notify`, `PlaySound`, `OpenExternal`, `AgentAction`. `ilium-server/src/plugin_host/intent_routing.rs` does not exist.
- K2 pane kinds. `ilium_ipc::NewPaneKind::Plugin { kind_id, title }` exists on the wire only. `ilium-core` has no plugin pane content kind (no `kind_id` in `ilium-core/src/lib.rs`) and the client draws no plugin pane, so board and editor panes cannot leave the kernel.
- K3 popups. `ilium-client/src/plugin_host/popup.rs` (the `Mode::PluginPopup` host) draws message lines, `paragraph`, `choice` and `check-list` only. Text inputs and scrolling exist in the right-hand panel views (`plugin_host/view.rs`, `views.rs`) and not in modal popups. A kernel dialog with text entry or a long scrolling list therefore cannot become a plugin popup. Wanted: `popup.rs` renders and edits `Widget::TextInput`, `Widget::NumberInput` and `Widget::ScrollView` with the same state as `view.rs`.
- K4 kernel to plugin calls. The kernel call sites of these features run synchronously inside kernel loops (server detection loop, server IPC handlers, the client selection path). A plugin answers asynchronously through events. Wanted: a kernel-side call, for example `PluginHost::call_service(plugin: &str, service: &str, payload_json: &str, deadline: Duration) -> Result<String, CallError>` on the server and `App::call_plugin_service(...)` on the client, with `CallError::Unavailable` when the plugin is disabled so the kernel feature is off while the plugin is off.
- K5 imports that are not equipped on a running plugin instance (`ilium-plugin-host/src/runtime.rs` instance import set and `wiring/wave_two.rs`): `clipboard` (`ClipboardImport` exists, used only by the testing harness), `editor` (`EditorImport`, harness only), `client-requests` (harness only). Skeletons without a backend: `inference` (`InferenceImport::new(ids)`, no provider call), `sounds` (`SoundsImport`), `audio`. `workspace` is an in-memory `WorkspaceImport` that is not backed by the kernel custody in `ilium-server/src/workspace*.rs`.
- K6 tree and terminal chrome. `ilium-client/src/terminal_context_menu.rs` lists no plugin entries and contributed toolbar buttons and row actions are not drawn (G6 is not built).
- K7 command line environment. There is no env or argv import in `wit/host/`. The `cli` import offers `caller-pane` and `selected-panes` only. A moved `ilium chat` needs `ILIUM_CHATROOM_AUTHOR`, `AGENT_NAME`, `ILIUM_PANE_ID`, the pane worktree variable `ilium_ipc::pane_env::WORKTREE`, optional hook JSON on standard input (`stdin: optional`; the manifest says `none`), and a project scope that reaches the main checkout of a linked worktree (the `fs` project scope is rooted at `Backends::project_dir` only).
- K8 settings. A contributed row is stored under `[plugins."<id>"]` in `config.toml`. The kernel tabs these plugins own are `[git]`, `[kanban_board]`, `[editor]`, `[text_triggers]`, `[triggers]` and `[icons]`, read by kernel code that must keep working (server workspace setup, `ilium-client/src/config.rs`). `settings.read-kernel:<tab>` and `settings.write-kernel:<tab>` work through `ConfigFileSettings`, but the running client and server do not reload after a plugin write and no `kernel-settings-changed` event exists (contract 20.5). Moving a tab needs both a migration of the stored keys and kernel readers that read the plugin store.
- K9 manual lock. The manual page and its REQ-tagged tests pin the manifests: for example `plugins/core/worktrees/tests/features/manifest.rs` line 240 asserts there is no `settings` contribution, and `plugins/core/text-triggers/tests/features/manifest.rs` asserts the exact grant lists. The group plan's contributions (settings rows with the built-in key names, extra grants, extension entries, a `plan` service) contradict those pins. They need a decision to change the manual page and the pins together; `tools/req_coverage.py` stays at exit 0 only while tagged tests are kept.

What the foundation does provide today (so a later move can use it): editable plugin settings rows in the Plugins list (`plugin_host/settings_rows.rs`), text input and scrolling in panel views (`plugin_host/view.rs`), link detectors (`plugin_host/links.rs`), the `process`, `fs`, `http` and `jobs` imports per instance, topics and services across sides, `SignalPane` and forwarded `OpenView`/`CloseView`, and `ilium <name>` routing to plugin CLI commands (`ilium/src/plugin_cli.rs`).
