# API gaps of the text-triggers feature tests

Items the tests call that the skeleton lacks, or manual details the tests had to assume.

- ilium-plugin-testkit: `FakeHost::output_filters(&self) -> Vec<(u64, ilium_plugin_sdk::primitives::OutputFilter)>` returns every output filter the plugin installed through `add-output-filter`, as (pane, filter). Requirement F-056 (page "Match output and answer"): the filter set is the observable channel of "each rule becomes one output filter on every agent pane".
- ilium-plugin-testkit: `FakeHost::set_hook_contributor(&mut self, point: &str, reply: HookReply)` registers a stub contributor of an extension point the plugin provides (here `before-fire`); the plugin must apply the reply (`refuse` stops the send, `pass` continues, a mode-forbidden reply counts as pass). F-056 (page "Extension points").
- ilium-plugin-testkit: `FakeHost::hook_calls(&self, point: &str) -> Vec<HookCall>` returns the hook calls the plugin made to the contributors of `point`. F-056 (payload: rule, pane, match, reply_length).
- ilium-plugin-testkit: `FakeHost::contribute_collect(&mut self, point: &str, entry_json: &str)` adds an entry to a collect point the plugin provides (here `rule-packs`). F-056. Assumption: the filter id of rule `i` of pack `p` is `<p>-<i>`; the manual does not state it.
- ilium-plugin-testkit: `FakeHost::published_topics(&self, topic: &str) -> Vec<String>` returns the JSON payloads the plugin published on a topic (here `ilium.core.text-triggers/fired`, payload `{ "rule", "pane" }`). F-056.
- ilium-plugin-testkit: `FakeHost::config_table(&self, table: &str) -> Option<serde_json::Value>` reads a table of the fake `config.toml`; `FakeHost::seed_config_table(&mut self, table: &str, value: serde_json::Value)` writes one (with unknown keys). COR-033, COR-011 ("keep unknown keys", same tables).
- ilium-plugin-testkit: `FakeHost::seed_settings_unchecked(&mut self, key: &str, value: serde_json::Value)` writes a setting without the row validation, as a hand edit of `config.toml` does; needed to render the invalid-pattern notice that the host would refuse to write. F-056 (page second figure).
- Manual gap (assumption in the tests): the page declares the list rows `patterns` and `replies` but not where rule names (`names`, the group titles "Confirm prompts") and enabled flags (`enabled`, list of bool in rule order) live; the tests use those two keys. The settings page view target is assumed to be `ViewTarget::SettingsPage("text-triggers")`, the filter id of rule `i` is `rule-<i>` (the page's toggle key), the rate is 2 per second, the session count key is `count/<filter id>` (little endian u64) and the `warn` level name is lower case.
- Manual gap: the page lists the service `ilium.core.text-triggers/test-rule` but its request and reply shapes are not stated, and `reference-test-harness.md` lists no service for this core stub; the tests only check the page text for it.
- Manual defect found by tests: the page's Extension points table marks `rule-packs` risk as `standard`, while `reference-extension-security.md` (SEC-293 corrected table) says `high`; the test `doc_293_rule_packs_is_high_risk_in_the_corrected_table_and_so_on_the_page` fails until the page is corrected.

## Ports part (tests/port)

- ilium-plugin-testkit: `FakeHost::call_service(&mut self, service: &str, request_json: &str) -> Result<String, ilium_plugin_sdk::types::PluginError>` calls a service the plugin provides (here `ilium.core.text-triggers/test-rule`). Requirement PORT:ilium-client/src/text_trigger_dialog/preview_tests.rs (all eight twins). Why: the dialog preview is only reachable through this service.
- Manual gap: `test-rule` request `{pattern, reply, sample}` and reply `{preview, issues}` are assumed; preview lines are `✓ a[bb]a` (match, bracketed), `· xxx` (no match), `✓ alpha  ⟪zero-width match⟫`, the loop warning `⚠ Reply also matches this regexp; echoed input can loop.`; issue `capture-limit` for a 1 MiB sample cut inside a scalar. Requirement PORT:ilium-client/src/text_trigger_dialog/preview_tests.rs.
- Manual gap: settings keys `delays` (list of integer seconds, default 60, 0..=86400, 0 sends immediately), `targets` (`agents`, `terminals`, `both`, default both) and `ids` (authored stable ids: non-blank, no control characters, unique) are assumed. Requirement PORT:ilium-ipc/src/text_trigger.rs (all six twins) and PORT:ilium-server/src/text_triggers.rs.
- Manual gap: a rule's reply is sent only after `delays[i]` seconds of host clock (`advance_clock`); the host dedup window is 10 minutes, so "fires again" twins use a clock gap above it. Requirement PORT:ilium-server/tests/text_triggers.rs::the_reply_waits_for_the_rules_delay_after_detection.
- Manual gap: tab row keys `delay-<i>` (Changed with Number or Text, blank means 60, clamped to 0..=86400) and `target-<i>` (Selected with Index 0 agents, 1 terminals, 2 both). Requirement PORT:ilium-client/src/text_trigger_dialog.rs.
- Manual gap: the trigger event actions tab (originals trigger_settings*.rs) is assumed to be `ViewTarget::SettingsPage("trigger-events")` over config table `[triggers]` with list settings `startup_complete`, `agent_waiting_background`, `agent_approval_required`, `agent_prompt_submitted`, `agent_finished_work` holding `retitle_element`, `restructure_project`, `restructure_all_projects`; toggle action keys are `<event>/<action>` and `<event>/none`; defaults as in the monolith. Requirement PORT:ilium-client/src/trigger_settings.rs and trigger_settings_ui.rs.
- Manual gap: an invalid source in the `[text_triggers]` table (not a table, missing patterns, non-list, bad regexp, empty pattern, multiline reply, duplicate ids, over 512 KiB) keeps the last valid rules and is not rewritten; an identical rewrite changes nothing. Requirement PORT:ilium-server/src/text_trigger_config.rs.
- ilium-plugin-testkit: `FakeHost::tree()` returns a handle with `add(TreeNode) -> u64` (used by the existing features tests); the ports additionally add a plain terminal pane with `agent: None`.

## Port wave notes (pure modules)

Moved into the plugin crate: `src/config.rs` (rule fields, defaults, table parsing, identity and candidate validation), `src/matching.rs` (instance identity, settle and resize windows, alternate screen tables, target filter, delivery ordering by due time; milliseconds instead of `Instant`, logical lines instead of a `vt100` screen). `regex = "1.13.0"` is added (already in `Cargo.lock`, G18). Plain tests in `tests/port/rules.rs`.

Not moved: `preview.rs`, `rows.rs` (client dialog and tab rows: G2 and G8, text entry), `lease.rs` (the session lease is a file lock beside the IPC socket, an OS decision that stays in `ilium-platform`), the matching job scheduling of `matching.rs` (kernel execution lanes). The FakeHost tests under `tests/features` and the other `tests/port` files stay red until real plugin wiring exists.

- G3: the server side cannot submit input, so `Tracker::evaluate` results are not yet delivered.
- G4: `ilium.core.terminal/screen-changed` and the terminal `transfer` service are same-side only for now, so the screen cannot be read.
- G10 (closed): the `clock` and `timers` imports are equipped for every instance, so a rule's delay runs on `timers.set`; a durable delay would use `timers.at`, which now survives a restart.
- G2/G8: the rules list is shown read-only.

## Move blockers (verified 2026-11-14)

The `text-triggers` kernel files stay PORT-KEEP after the gap streams. The list below is the exact reason per file; the cuts file `docs/tasks/02-cuts/text-triggers.md` carries the key table.

- `ilium-server/src/text_triggers.rs`, `text_triggers/matching.rs`: run on the server screen path and submit the reply as input (K4, K1). The plugin reads the screen through `ilium.core.terminal/screen-changed` and `transfer` (cross-side topics and services exist), but cannot deliver the reply (K1).
- `ilium-server/src/text_trigger_config.rs`: read at server start from `[text_triggers]` (K8). `ClientRequest::UpdateTextTriggers` stays.
- `ilium-client/src/text_trigger_dialog*.rs`, `trigger_settings*.rs`, `trigger_execution_lease.rs`: the Settings tab editor has text entry (K3, K8); the lease is an OS file lock beside the IPC socket and stays in `ilium-platform`.
- The manual page describes an output-filter design (`terminal.output-filter`, exact grant lists pinned by `tests/features/manifest.rs`), the group plan a `screen-changed` subscription with `topics.subscribe` and `settings.read-kernel`. They disagree, K9.

Blocker keys (verified against the tree on 2026-11-14; each names the exact missing piece):

- K1 intents. `ilium-server/src/plugin_host/facade.rs` `apply_intent` routes only RenameNode, MoveNode, CloseNode, SetNodeLocked, CreatePane, ResizePane, CreateGroup, CreateSplit, SetBookmarked, SetExpanded, Message, SetStatusSegment, ClearStatusSegment, SetDecoration, ClearDecoration, SignalPane, OpenView and CloseView. Every other arm ends in `unsupported("this intent")`: `Intent::SendInput` (needs `Delivery::{Typed, Submitted, Pasted}` plus `stages` / `prompt_epoch` mapped to the server requests `UserKeyInput`, `SubmitTerminalText`, `PasteTerminalText`, `SchedulePaneInput`), `EditorOpen`, `ApplyEdits`, `Notify`, `PlaySound`, `OpenExternal`, `AgentAction`. `ilium-server/src/plugin_host/intent_routing.rs` does not exist.
- K2 pane kinds. `ilium_ipc::NewPaneKind::Plugin { kind_id, title }` exists on the wire only. `ilium-core` has no plugin pane content kind (no `kind_id` in `ilium-core/src/lib.rs`) and the client draws no plugin pane, so board and editor panes cannot leave the kernel.
- K3 popups. `ilium-client/src/plugin_host/popup.rs` (the `Mode::PluginPopup` host) draws message lines, `paragraph`, `choice` and `check-list` only. Text inputs and scrolling exist in the right-hand panel views (`plugin_host/view.rs`, `views.rs`) and not in modal popups. A kernel dialog with text entry or a long scrolling list therefore cannot become a plugin popup. Wanted: `popup.rs` renders and edits `Widget::TextInput`, `Widget::NumberInput` and `Widget::ScrollView` with the same state as `view.rs`.
- K4 kernel to plugin calls. The kernel call sites of these features run synchronously inside kernel loops (server detection loop, server IPC handlers, the client selection path). A plugin answers asynchronously through events. Wanted: a kernel-side call, for example `PluginHost::call_service(plugin: &str, service: &str, payload_json: &str, deadline: Duration) -> Result<String, CallError>` on the server and `App::call_plugin_service(...)` on the client, with `CallError::Unavailable` when the plugin is disabled so the kernel feature is off while the plugin is off.
- K5 imports that are not equipped on a running plugin instance (`ilium-plugin-host/src/runtime.rs` instance import set and `wiring/wave_two.rs`): `clipboard` (`ClipboardImport` exists, used only by the testing harness), `editor` (`EditorImport`, harness only), `client-requests` (harness only). Skeletons without a backend: `inference` (`InferenceImport::new(ids)`, no provider call), `sounds` (`SoundsImport`), `audio`. `workspace` is an in-memory `WorkspaceImport` that is not backed by the kernel custody in `ilium-server/src/workspace*.rs`.
- K6 tree and terminal chrome. `ilium-client/src/terminal_context_menu.rs` lists no plugin entries and contributed toolbar buttons and row actions are not drawn (G6 is not built).
- K7 command line environment. There is no env or argv import in `wit/host/`. The `cli` import offers `caller-pane` and `selected-panes` only. A moved `ilium chat` needs `ILIUM_CHATROOM_AUTHOR`, `AGENT_NAME`, `ILIUM_PANE_ID`, the pane worktree variable `ilium_ipc::pane_env::WORKTREE`, optional hook JSON on standard input (`stdin: optional`; the manifest says `none`), and a project scope that reaches the main checkout of a linked worktree (the `fs` project scope is rooted at `Backends::project_dir` only).
- K8 settings. A contributed row is stored under `[plugins."<id>"]` in `config.toml`. The kernel tabs these plugins own are `[git]`, `[kanban_board]`, `[editor]`, `[text_triggers]`, `[triggers]` and `[icons]`, read by kernel code that must keep working (server workspace setup, `ilium-client/src/config.rs`). `settings.read-kernel:<tab>` and `settings.write-kernel:<tab>` work through `ConfigFileSettings`, but the running client and server do not reload after a plugin write and no `kernel-settings-changed` event exists (contract 20.5). Moving a tab needs both a migration of the stored keys and kernel readers that read the plugin store.
- K9 manual lock. The manual page and its REQ-tagged tests pin the manifests: for example `plugins/core/worktrees/tests/features/manifest.rs` line 240 asserts there is no `settings` contribution, and `plugins/core/text-triggers/tests/features/manifest.rs` asserts the exact grant lists. The group plan's contributions (settings rows with the built-in key names, extra grants, extension entries, a `plan` service) contradict those pins. They need a decision to change the manual page and the pins together; `tools/req_coverage.py` stays at exit 0 only while tagged tests are kept.

What the foundation does provide today (so a later move can use it): editable plugin settings rows in the Plugins list (`plugin_host/settings_rows.rs`), text input and scrolling in panel views (`plugin_host/view.rs`), link detectors (`plugin_host/links.rs`), the `process`, `fs`, `http` and `jobs` imports per instance, topics and services across sides, `SignalPane` and forwarded `OpenView`/`CloseView`, and `ilium <name>` routing to plugin CLI commands (`ilium/src/plugin_cli.rs`).
