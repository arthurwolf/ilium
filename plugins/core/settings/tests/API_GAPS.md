# API gaps found by the settings features tests

- ilium-plugin-testkit: `impl FakeHost { pub fn published_topics(&self) -> Vec<(String, String)> }` (F-090): `(topic, payload_json)` of every topic publication, in order. Needed by tests/features_gaps for `ilium.core.settings/changed`.
- ilium-plugin-testkit: `impl FakeSession { pub fn call_extension(&mut self, point: &str, payload_json: &str) -> Result<Vec<String>, HarnessError> }` (F-089, F-090): collect the contributions of an extension point the plugin owns. Needed by tests/features_gaps.
- ilium-plugin-core-settings: the skeleton exports only `views`; the page lists services `ilium.core.settings/get` and `/set` and the topic `changed`, so the client struct needs `exports = ["views", "service-provider"]` (or equivalent) and the manifest needs `services.offer`, `topics` and `extensions.provide:*` grants/contributions. The manifest is declared exact by the page, so the manual must say which is right; the service tests assume the plugin answers them.
- manual: the request and reply JSON of the `get` and `set` services is not specified. Tests assume request `{ "key": ..., "value": ... }` and reply `{ "value": ... }`, `invalid-argument` for malformed JSON, a missing key or an invalid value, and `not-found` for an unknown service name (F-090).
- manual: the setting keys of the kernel tabs are not specified. Tests assume the dotted keys of the `config.toml` tables listed in src/docs/settings.md (`ui.motion_level`, `ui.left_panel_fixed_width`, `theme.accent_bg`, `debug.file_logging_enabled`, ...) in `FakeSettings`, and the manifest row keys `density` and `accent` undotted (F-086, F-090, F-092).
- manual: the Icons tab keys under `[ui.icons]` (role names) are not specified, so the Icons tab values are not tested beyond the table of owned tabs (F-090).
- manual: the page defines no behaviour ids `settings-Bnn`; behaviours are covered through F-086, F-089, F-090, F-091, F-092 and src/docs/settings.md.
- ilium-plugin-testkit: `FakeSettings::set` for a value outside the allowed set or range: tests assume `Err(PluginError { code: InvalidArgument, message })` with the key named in `message` (settings.md: "a message naming the key"), `null` resetting to the default (reference-settings-rows.md, RFC 7396), and an unknown key refused with `invalid-argument` (F-090).
- manual: how `send_action` encodes a toggle, a choice, a number and Enter is not specified. Tests assume `Toggled`+`Flag`, `Changed`+`Text` for choices and colours, `Changed`+`Number` for numbers, `Submitted` for Enter, sent to `SettingsPage("<tab id>")` with the setting key as the widget key; the 600 ms rule is tested as a debounce on the fake clock (F-090).
- manual: the word `Saved` of the figure (settings tab) is asserted as present after a change; its lifetime is not specified (F-090).
- manual: how the plugin learns the plugin list for the Plugins tab (ids, tiers, states) is not specified; the view id `SettingsPage("plugins")` and the 58 x 10 render size are assumed from the figure (caption says 48 columns, the figure is 58 wide). The golden tests/features/golden/plugins_tab_58.txt is the page figure verbatim (F-090, USR-162).
- manual: the first two figures of the page are rendered with inconsistent widths (caption says 48 columns, the text is 190 to 230 cells wide), so they are not pinned as goldens; the settings tab and the onboarding step are tested by text at widths 40, 80 and 120 (F-089, F-090).
- manual: the manifest names a settings section `first-run` only in a comment; manifest.json has no such section, so the content of the `first-run` step form is not tested beyond title, hints and position text (F-089).
- manual: "automatic AI stays off until the setup finishes" and "the setup keeps its own state until the user finishes" (page, Guided setup) name no key or channel; not tested (F-089).
- manual: Forget settings (USR-163), the plugin page tabs and the `[ Open Plugins page ]` link name no view ids or actions; only the page text is tested (F-090).
