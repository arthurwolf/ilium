# API gaps found by the notifications features tests

- ilium-plugin-core-notifications: `pub struct NotificationsClient` (`#[ilium_plugin(side = "client", exports = [])]`, `Default`, `Lifecycle`, `Handler`) is missing from src/lib.rs; the page says the plugin runs on both sides and holds the client grants `notify.toast` and `settings.write-kernel:sound`, but the skeleton has only `NotificationsServer`. Needed by tests/features_gaps (F-047, F-048, F-049).
- manifest / manual: manifest.json has no `client` entry (`{"entry": "client.wasm", "world": "ilium:client/base@0.1.0"}`) although the page says the plugin runs on both sides and lists client grants. The tests follow COR-050 (manifest equals the Complete manifest block) and do not assert a client entry; the manual must say which is right.
- manifest / manual: the manifest has no `contributes` (commands `open-pane` and `dismiss-toast` of page sample 3, `contributes.sounds` of samples 1 and 2, the extension points `before-notify` and `channels`, the service `notify`, the topic `raised`, `extensions.provide:*`, `services.offer`, `topics` grants). The page says the manifest is exact, so the contribution ids are unspecified. The tests assume the command id `ilium.core.notifications/dismiss-toast` (ends with `/dismiss-toast` per the sample) and `ilium.core.notifications/open-pane`, and that the toast id is `finished-<node number>` (F-048).
- manual: the page defines no behaviour ids `notifications-Bnn`; the behaviours are covered through F-047, F-048, F-049 and the user guide src/docs/notifications.md.
- ilium-plugin-testkit: `impl FakeHost { pub fn published_topics(&self) -> Vec<(String, String)> }` (F-048): `(topic, payload_json)` of every topic publication the plugin made, in order. Needed by tests/features_gaps/topic.rs for `ilium.core.notifications/raised`.
- ilium-plugin-testkit: a way to invoke an extension point the plugin owns with contributors (`before-notify` veto, `channels` collect), for example `FakeSession::call_extension(point: &str, payload_json: &str) -> Result<Vec<String>, HarnessError>` (F-048); the tests only read the page tables until it exists.
- manual: how the plugin learns about monitored task outcomes is not specified. The tests assume a `TopicPublished` event of topic `ilium.core.progress/changed` (reference-core-extension-points.md lists `{ monitor, status, percent }`) with the extra fields `pane` (node number) and `job_id`, and `status` one of `running`, `done`, `error`, `lost` (`lost` stands for a monitor whose health failed). F-047, F-048, F-049.
- manual: the setting keys the plugin reads and how a change reaches it are not specified. The tests assume dotted keys of the config tables (`notifications.enabled`, `notifications.agent_finished`, `notifications.approval_required`, `notifications.task_succeeded`, `notifications.task_failed`, `notifications.suppress_redundant_task_outcomes`, `notifications.task_coalesce_seconds`, `sound.source`, `sound.file`, `sound.events.<event>`, `sound.design.<key>`) in the `FakeSettings` of the host, announced with `Event::KernelSettingsChanged { tab: "sound", keys }` (F-047, F-048, F-049).
- manual: the sound ids per event are not specified. The tests take them from the Sounds figure of the page: approval -> `ask`, agent finished -> `finished`; other events are only asserted to play exactly one sound (F-047).
- manual: the desktop and sound text rely on the session name (`Session "<name>": ...` in the body) and on the short and long pane titles (`About: <description>` paragraph); the plugin API gives neither, so the tests assert only the title and the end of the body. How the plugin gets the session name and the long title is unspecified (F-048).
- manual: "waiting for background work" (sound event `waiting_background`) and "parked" agents have no `AgentActivity` case; the tests cover only its default (off) and the redundant-outcome rule for idle and finished agents (F-047, F-049).
- ilium-plugin-testkit: `FakeSettings::set` for an invalid value or a key outside the tab: the tests assume `Err(PluginError { code: ErrorCode::InvalidArgument, .. })` and clamping (`Ok`, stored value clamped) for numbers outside their range, as src/docs/notifications.md says "Out-of-range values are clamped". The validation messages are not specified by the manual (F-047, F-049).
- ilium-plugin-testkit: the storage bucket of the `muted` flag (page sample 5) is not specified; the tests assume `Bucket::Global` (F-047).
- ilium-plugin-testkit: the argument format of `FakeSession::call_service` (version range `^0.1`) and the JSON of the `notify` service (`{ title, body, urgency }`) and its error codes are not specified; the tests assume `invalid-argument` for a missing title, an unknown urgency word or malformed JSON, and `not-found` for an unknown service name (F-048).
- manual: the page sample 1 lists `NotifySpec` with four fields while the generated type has six (`body: Option<String>`, `coalesce_key`, `coalesce_window_ms`); the tests use the generated type.
- manual: how a node counts as "seen" before `ack-attention` (page sample 4, `self.seen(node)`) is not specified; the tests assume the node is the focused pane (`Event::PaneFocused(Some(node))`) (F-048).
- ports (tests/port): ilium-plugin-sdk `AgentActivity` has no waiting-background or background-task case (ilium-server/src/notifications.rs ports); the twins drive both as `Working`, which is what the original NowSignal projection does (busy), so `working_to_waiting_background_*`, `waiting_background_to_*` and `background_task_still_running_*` are asserted as Working transitions.
- ports (tests/port): ilium-plugin-testkit `FakeHost` cannot change the `goal` of an agent already in the tree (`TreeNode.agent.goal` is set only at `add`); the goal twins create the pane with a goal and cannot assert the "goal clears on completion" half of `agent_with_goal_working_to_plain_agent_done_notifies_when_goal_clears_on_completion`. Needed: `FakeTree::set_goal(id: u64, goal: Option<&str>)` and an `Event::AgentGoalChanged` delivery (reference-wit.md 4.13).
- ports (tests/port): the plugin API gives no session name and no long pane description; the twins read the long description from `AgentView.objective` (assumed) and assert the `Session "` prefix only.
