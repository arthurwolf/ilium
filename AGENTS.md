# Compilation policy

### Distributed compilation through ni-build

- All compilation MUST run on `ni-vm`, never locally. Use the installed whole-job `ni-build` service through authenticated `ssh ni-vm`; never connect separately to `ni`. Rust's configured local `cargo` and `rustc` entrypoints dispatch to this service. Examples: `cargo build --release`, `cargo check`, `cargo test`, `cargo clippy`, or explicit `ni-build cargo ...`. The complete Cargo command, native build scripts, procedural macros, linking and tests execute remotely. sccache per-crate offload alone does not satisfy this rule.
- The dispatcher automatically inventories current source/workspace/path-dependency inputs, transfers a hashed isolated snapshot, selects the requested installed toolchain, retrieves verified artifacts and logs, and cleans its exact remote job after successful evidence retrieval. Do not repeat the former manual copy/build/scp workflow. Job directories are `/data/ni-build-service/jobs/<uuid>/`; evidence and immutable returned outputs are under `~/.local/share/ni-build/receipts/<uuid>/`. Use a job receipt to identify the exact checked source and remote exit status.
- Git projects include dirty tracked and nonignored new sources. List required ignored assets explicitly in `.ni-build-inputs`, one project-relative file or directory per line. Missing or unsupported inputs/options fail closed. Do not override the compiler guard, invoke raw local toolchain binaries, use `rustup run` to bypass dispatch, or fall back to local compilation when remote access/toolchains are unavailable. Report and repair the route instead. Configuration prevents accidental ordinary-command compilation; an unrestricted user can deliberately bypass it, which policy prohibits.
- Remote execution uses `nice`/`ionice`, at most 16 allowed CPUs, Cargo jobs at most 16 and capped native child parallelism. Preserve other owners' jobs/files. Capacity is checked before transfer. Failed transfer, source validation or artifact verification retains the exact job for recovery; remove it only after retrieved evidence/artifacts are verified and no process needs it. Never remove `/data` itself or another task's directories.
- Select targets/toolchains compatible with the local consumer; remote compilation does not prove local runtime behavior or activation of a running service. Verify returned artifacts before use and separately verify required local runtime behavior. Existing progress-monitor notification and process-custody rules apply unchanged.
- Non-Rust compilation must also execute through a whole-job remote route on ni-vm; a local compiler invocation or local fallback is forbidden. Unsupported toolchains require extending and verifying the remote service before use.
- Service configuration, supported options, recovery and rollback: `~/.local/share/ni-build/README.md`. Do not replace the `~/.codex/AGENTS.md` symlink; edit its target `~/.claude/CLAUDE.md`.

For every task expected to take at least three minutes inside an Ilium pane, you MUST use an Ilium progress monitor. Start the task in the background, detached so it outlives the shell command that started it (e.g. `setsid -f`; some agent shells kill `&` children when the command returns), and verify that its process is alive. Write a cheap probe that prints one JSON object: stable non-empty `job_id`, `status` (`not-started-yet`, `running`, `error` or `done`), finite `percent` 0 to 100, one-line `message`, optional multi-line `details`, and `error` only when status is `error`. The Ilium server runs it from the project root without your shell's directory, variables or aliases: use absolute paths.

The reader of the progress bar has NOT read your session. `message` (at most about 110 characters) MUST stand alone: WHAT is being done to WHICH thing, then the current step with a count, e.g. `Building the release binaries of the ilium terminal app - compiling crate 14 of 22`; when finished, the outcome. `details` has 3 to 8 short lines labelled `What:`, `Why:`, `Now:` (with what `percent` measures), `Next:`, `Watch:`. Never rely on session context: no unexplained internal names, abbreviations or pronouns. Update both on every probe run.

Run `ilium progress check --command '<probe>'`, then register and wait with one command: `ilium progress set --command '<probe>' --interval-seconds <n> --wait`. Its first line is the positive JSONL registration acknowledgement with the monitor ID; it then blocks until the task ends and prints a `progress_wait` line. Exit status: 0 done, 3 task error, 4 monitor failed (outcome unknown: check the task directly), 5 monitor replaced or cleared, 6 `--timeout-seconds` elapsed (run `ilium progress wait <monitor_id>` to keep waiting). If your shell tool limits command run time, pass `--timeout-seconds` below the limit, or run the command in the background if your tool reports when it exits. If the tool hands back a still-running command, keep waiting on that same command with the longest wait the tool allows (Codex: `yield_time_ms` 300000 on every `write_stdin` or cell wait); never start a second one. This wait takes precedence over any general rule about sleep loops or wait lengths. If `ilium` rejects `--wait` or `progress wait` as unknown (an older Ilium build), register without `--wait` and handle the typed message instead.

With other useful work to do, register without `--wait` and do it: Ilium's server will send you a message when the task reaches `done` or `error` (or run `ilium progress wait` later). A subagent, or anything else that cannot receive typed messages, MUST use `--wait`.

You MUST NOT poll in any form: no sleep loops, repeated `ilium progress status`, or repeated log reads. Ilium's server is the sole recurring poller.

A pane has one monitor. `set` refuses with `monitor-active` while it is still running: cover a multi-step pipeline with one probe, or wait for your own task directly. `--replace` discards the running monitor; use it only on purpose. If `progress_wait` says `composer_notice` `may-also-arrive`, a typed message about that monitor is a duplicate. After handling a result, `ilium progress clear --monitor-id <id>` removes it.

**A progress monitor tracks one job attempt, not the user's goal. A failed build/test or a missing, invalid, or unobservable monitor does not end or block the goal.** Keep the original user outcome and its acceptance checklist active until they pass or the user explicitly changes or stops the request. A response ending, wait, notification delay, compaction, or failed attempt is not a goal transition. Never call a goal-status tool to represent waiting or failure. Mark the goal `blocked` only when the same underlying condition independently prevents all meaningful progress for at least three consecutive goal turns and user input or an external-state change is required.

**A running monitor is not a stop condition.** While it runs, continue every checklist item that does not need its result: inspect or edit other relevant source, review the acceptance path, prepare independent evidence, or fix an unrelated failed prerequisite. Do not wait merely because a bar is visible. When those independent actions are exhausted and the monitor's result is the sole remaining dependency, block on it with `ilium progress wait <monitor_id>` (its exit status returns the outcome in the same turn), or end the current response naming that exact dependency and resume the same goal when notified. This response boundary is not a pause, handoff, or change to goal status.

**Required procedure when a user pastes a monitor report:**
1. Recover the original request and list the acceptance steps that remain. Treat the pasted report as an event in that work, not as a replacement request for a status explanation.
2. For `done` or `error`, inspect only that terminal attempt's retained evidence once. If it succeeded, verify the result and continue to the next acceptance step. If it failed, correct the cause or choose another route, then launch the needed retry yourself and continue the same checklist.
3. For `running`, `unknown`, missing, malformed, or unobservable status, do not poll, probe, read evolving output, clear, restart, duplicate, or otherwise disturb the job. Preserve its identity and do checklist work that does not depend on it. Do not infer success or failure from missing visibility.
4. Before replying, ask whether any useful checklist work is independent of the monitor. If yes, do that work before replying. If no, state the job/monitor identity, the exact result that is pending, and that the same goal remains active for notification and continuation. Ending that response does not end the goal.
5. A status explanation is not progress. Saying “the goal remains active,” apologizing, or promising to continue later does not satisfy this procedure when useful checklist work can be done now. If the user asks why progress stopped, answer briefly and resume the original checklist in the same turn. Never reply only with the monitor percentage/error, ask the user to restart or reissue the task, or stop at reporting a failed attempt.

**Counterexample:** “The build is still running, so I’ll wait” is wrong whenever any independent checklist action remains. “The test failed; the goal is blocked” is wrong until the failed attempt's retained evidence has been inspected once and a repair or reroute has been tried. The only monitor-based reason to end a response is that every remaining acceptance item depends on that exact active/unobservable job; preserve it and continue on notification.

**Do not stop in practice while claiming the goal is active.** A response that explains a failed/unknown monitor and then ends, with no next action performed, is still a stop if useful checklist work was available—even if no goal-status tool was called and the response says “I’ll continue later.” After the short explanation, take the next safe checklist action before replying. Only when the monitor is the sole remaining dependency may you end the response without further work; preserve the same goal and wait for that monitor’s notification rather than creating a new goal, asking the user to reissue the task, or changing goal status.

**Every terminal report must produce a next action in the same turn.** A failed source snapshot means repair the snapshot path and retry it. A test failure means inspect that attempt's retained evidence once, fix the cause, and rerun the acceptance step. A successful attempt means verify its evidence and move to the next acceptance step. An unknown or unobservable attempt means preserve it without probing and do independent checklist work. For example, “source changed or rsync failed” does not end the feature task: recover the snapshot and continue. “Regressions exited with status 101” is a failed test attempt, not the user's outcome: diagnose the retained failure and rerun the gate. Before replying, identify and perform the next checklist action unless the monitor is the sole remaining dependency or an explicit safety/authority boundary prevents progress.

Examples: a failed source snapshot means repair the transfer/snapshot path and retry; a test exit such as status 101 means inspect that attempt's retained failure evidence, fix the cause, and rerun the acceptance step; an unobservable monitor means preserve its job ID and continue independent work without inspecting its output.

If the monitored job is the only remaining dependency, block on `ilium progress wait <monitor_id>`, or end only the current response: report the job and monitor IDs, the specific dependency, and that the same goal remains active for notification and continuation. When notified or resumed, continue that same goal. Do not ask the user to restart it, create a replacement goal, or treat a response ending, wait, notification delay, or compaction as a goal transition.
