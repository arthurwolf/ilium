## Host runtime

This page fixes how the host uses Wasmtime: which version, which build features, which `Config` values, how a component becomes a running instance, how imports are linked, what WASI the host offers, how time limits are enforced and what the host checks when a package is installed. A test author uses it to write the conformance and safety tests of the runtime. A host implementer uses it as the configuration to copy.

The requirement ids `[HST-050]` to `[HST-089]` belong to this page. They are collected, with a test method each, in [Requirements: kernel and host](/pages/reference-requirements-kernel-host/).

## You will need

- [Host architecture](/pages/reference-host-architecture/) for the processes that own an Engine and for the rule that T2 and T3 components run in a helper.
- [Scheduling, deadlines and cancellation](/pages/reference-host-scheduling/) for the call classes and their deadlines.
- A basic idea of Wasmtime. A **component** is a WebAssembly binary that follows the component model: it declares typed imports and exports instead of raw functions. A **`.cwasm`** file is a component that Wasmtime has already compiled to machine code for one target and one configuration. An **`InstancePre`** is a component whose imports have been resolved against a linker, so each new instance skips that work.

## Version policy

- **[HST-050]** Each Ilium release MUST pin Wasmtime to one exact version in `Cargo.lock` and in the workspace manifest (`=` requirement). The version at the time this contract was written is 49.0.2, which needs Rust 1.96 or later. The version in use is shown by `ilium plugin doctor` and recorded in every `.cwasm` header and in every benchmark result.
- **[HST-051]** A Wasmtime security release that fixes a vulnerability reachable from guest code MUST be taken into a point release of Ilium within 14 days of the upstream fix (see [SEC-171]), and within 48 hours when the vulnerability is exploited in the wild.
- **[HST-052]** A Wasmtime version bump MUST NOT be merged until all of these pass on the new version: the full conformance suite for the Rust and TypeScript guests, the benchmark gate of [Performance budgets and benchmarks](/pages/reference-host-budgets/) with no regression beyond its thresholds, the test that every embedded `.cwasm` deserializes, and the safety tests listed under "Errors and edge cases" below.
- **[HST-053]** Every embedded `.cwasm` MUST be regenerated by the release build on every Wasmtime bump and on every change of a `Config` value that affects code generation. A stale `.cwasm` MUST fail the build, never ship.

## Build features and Config

The host depends on Wasmtime with `default-features = false`. The features are exactly these.

| Feature | State | Why |
|---|---|---|
| `runtime` | on | Execution |
| `cranelift` | on | Compiling third-party and development components; precompiling bundled ones in the release build |
| `component-model` | on | Plugins are components |
| `std` | on | Host platform support |
| `parallel-compilation` | on | Faster first load of a large third-party component |
| `async` | on | `call_async`, `instantiate_async`, epoch yield |
| `cache` | on | The compile cache for third-party components |
| `component-model-async` | off | Not needed by contract version one; keeping it off keeps the host outside the affected code of CVE-2026-27195 |
| `winch`, `gc`, `threads`, `profiling`, `coredump`, `debug-builtins` | off | Not used; each adds attack surface or size |

- **[HST-054]** The host MUST build Wasmtime with exactly the feature set above, and a workspace test MUST fail when `component-model-async` is enabled.

The `Config` values are fixed. The same values apply in the release build that produces `.cwasm` files and in the running host, because a `.cwasm` only loads on an Engine whose relevant configuration matches.

| Setting | Value | Notes |
|---|---|---|
| `wasm_component_model(true)` | on | |
| `wasm_component_model_async(false)` | off | See `[HST-055]` |
| `async_support(true)` | on | All guest calls use the async API so that epoch yields and cancellation work |
| `epoch_interruption(true)` | on | Time limits; see the epoch section |
| `consume_fuel(false)` | off | Fuel adds a counter update to every basic block and costs more than epoch checks; epoch checks are enough because the contract limits wall time, not instruction counts |
| `max_wasm_stack` | 512 KiB | Stack overflow is a trap |
| `async_stack_size` | 1 MiB | Must be at least `max_wasm_stack`; stacks are allocated per call in flight, not per instance |
| `memory_reservation` | 4 GiB on 64-bit targets | Virtual address space only; lets the host use guard pages instead of explicit bounds checks |
| `memory_guard_size` | 32 MiB | Wasmtime default for 64-bit targets |
| `signals_based_traps(true)` | on for Linux, macOS and Windows | The server and client MUST NOT install their own SIGSEGV, SIGBUS or SIGILL handlers; on macOS the host uses Mach exception ports |
| `parallel_compilation(true)` | on | |
| `cranelift_opt_level(Speed)` | speed | |
| `wasm_simd(true)` | on | The Rust scenes use SIMD128 |
| `wasm_relaxed_simd(false)` | off | Relaxed SIMD results depend on the CPU, so a scene would render differently on two machines |
| `wasm_threads(false)`, `wasm_multi_memory(false)`, `wasm_memory64(false)`, `wasm_gc(false)` | off | Not part of the contract |
| `generate_address_map(true)`, `wasm_backtrace(true)` | on | Release traps show function names |
| `debug_info(false)` | off | `ilium plugin build --debug` is a plugin-side concern |
| `cache` | see "Compile cache" | |

- **[HST-055]** The host MUST set `wasm_component_model_async(false)`. A component that needs it MUST be refused at load with `component.invalid`.
- **[HST-056]** The host MUST fix the `concurrency_support` setting at build time to the value that keeps Wasmtime's concurrency APIs unused, and a test MUST instantiate, call and drop a component under that setting. (Disabling it makes those APIs panic, so the host never calls them.)
- **[HST-057]** The `Config` values in the table MUST be identical in the release build that produces `.cwasm` and in the host, and the host MUST compute a `config fingerprint` (a hash of Wasmtime version, target triple and every value in the table) and store it in the header of each embedded artifact.
- **[HST-058]** Epoch interruption MUST be on, and fuel MUST be off.
- **[HST-059]** `max_wasm_stack` MUST be 512 KiB and `async_stack_size` MUST be 1 MiB.
- **[HST-060]** Signals-based traps MUST be enabled on every supported platform, and the Ilium processes MUST NOT install handlers for SIGSEGV, SIGBUS or SIGILL on Unix.

### Compile cache

Third-party components are compiled on first load. The host stores the compiled code in the Wasmtime compile cache so that later loads are fast.

| Property | Value |
|---|---|
| Location | `<cache dir>/ilium/plugins/compile/<wasmtime version>-<config fingerprint>/`, owner-only (mode 0700); entries inside are keyed by the component hash, and the config fingerprint includes the CPU features |
| Size cap | 1 GiB total (`files-total-size-soft-limit`), 4,096 files |
| Eviction | Wasmtime's cleanup removes least recently used entries when a cap is reached |
| Invalidation | The directory name contains the Wasmtime version and the config fingerprint. At startup the host deletes every sibling directory with another name |
| Who writes | The host process that compiled the component, or for T2 and T3 the helper that compiled it, in its own subdirectory `<package hash>/` (see [Sandbox helper](/pages/reference-host-helper/)) |

- **[HST-061]** The compile cache MUST be owner-only, MUST be keyed by Wasmtime version and config fingerprint, and the host MUST delete caches of other keys at startup.
- **[HST-062]** The host MUST work with an unreadable, unwritable or full compile cache by compiling in memory and logging `host.cache-unavailable` once.

## Allocator

The default is the **on-demand allocator**: each instance gets its memory from the operating system when it is created. This is decision D6 of [Design decisions](/pages/design-decisions/).

The **pooling allocator** reserves a fixed number of instance slots at start. It makes instantiation faster and bounds address space, but it reserves virtual memory for the largest slot.

- **[HST-063]** The host MUST use the on-demand allocator unless the benchmark rule below selects pooling.
- **[HST-064]** The benchmark B6 selects pooling if and only if both of these hold on the reference machine class: on-demand misses `HOST-START` (150 ms for the 40-plugin bundled set) or the instantiate time `B2` (5 ms median), and pooling meets both while adding no more than 16 MiB RSS. A selection MUST be recorded in the benchmark results page together with the Wasmtime version.

If pooling is selected, the pool is sized as follows: `total_core_instances` 256, `total_memories` 256, `total_tables` 256, `total_stacks` 64, `max_memory_size` equal to the T1 ceiling of `memory_mib` (256 MiB), `table_elements` equal to the T1 ceiling of `table_elements` (50,000), and `max_core_instance_size` 1 MiB. Pooling is used for T1 and for helper Engines alike; an Engine never mixes allocators.

### Loading a component

- **[HST-065]** `Component::deserialize` MUST be used only for artifacts that the release build of this exact Ilium version produced with the host's Engine `Config`. It MUST NOT be called on bytes from a package, a download, a user path or a cache that the host did not write.
- **[HST-066]** A test MUST deserialize every embedded `.cwasm` on the host Engine and MUST fail the build if any artifact is rejected.
- **[HST-067]** T2 and T3 components MUST be loaded with `Component::new` (inside the helper), through the compile cache, and the host MUST NOT call `Component::deserialize` on package bytes. The Wasmtime compile cache is the only path that deserializes, and it reads only files that the same host wrote under its owner-only cache directory.
- **[HST-068]** A package that contains a `.cwasm` file MUST be refused at install with `package.precompiled-forbidden`.

### InstancePre and Linker

- **[HST-069]** The host MUST build one `InstancePre` per plugin side and MUST rebuild it whenever the grant set of that plugin changes (grant, revoke, upgrade). Existing instances keep running until they are re-activated as described in [Lifecycle](/pages/lifecycle/).
- **[HST-070]** The host MUST build one `Linker` per distinct grant set and MUST cache it under the SHA-256 of the sorted list of granted interface names plus the side and the tier. Two plugins with equal grant sets on equal sides share a `Linker`.

How an import is linked depends on what the manifest requested and what the user granted. Two levels exist, because a capability is finer than an interface: the interface `fs` has functions for reading and for writing, and the grants `fs.read:project` and `fs.write:project` unlock different ones.

| Case | Interface level (static) | Function level (dynamic) |
|---|---|---|
| Always-granted interface | Linked with real functions | Real functions |
| Capability requested and granted | Linked with real functions | Real functions |
| Capability requested and declined or revoked | Linked | The functions of that capability are stubs that return `not-permitted` |
| Capability never requested, but another capability of the same interface was | Linked | The functions of the unrequested capability trap with `host.capability-not-requested` (a plugin bug) |
| Interface that no requested capability unlocks and that is not always granted | The package is refused at install or load with `manifest.import-not-requested`; nothing is instantiated | Not applicable |

This is the reconciliation of the two earlier statements. A component whose binary imports an interface that its manifest never requested cannot be linked, so it never runs and never traps; it is refused when it is installed or loaded. A call to a single function whose capability was not requested, inside an interface that was linked for another reason, still traps at call time, because the host cannot refuse the interface. Both rules agree with [Capabilities and grants](/pages/capabilities/): a declined grant returns `not-permitted`, a never-requested one is a plugin bug.

- **[HST-071]** A declined or revoked capability MUST link its functions to stubs that return `not-permitted` without running kernel code.
- **[HST-072]** A component that imports an interface that is neither always granted nor unlocked by a requested capability MUST be refused at install or load with `manifest.import-not-requested`, and MUST NOT be instantiated.
- **[HST-073]** A call to a function whose capability the manifest never requested, inside a linked interface, MUST trap the instance with `host.capability-not-requested` and count as a failure.

## Store setup

Each Store is created with limits and data from the manifest `limits` after clamping to the tier ceiling (see [Errors and limits](/pages/reference-errors-and-limits/)).

| Store limit | Source | On growth failure |
|---|---|---|
| Memory (bytes) | `memory_mib` for the main instance, `job_memory_mib` for a job instance | Trap. The guest never observes -1 [ABI-027] |
| Table elements | `table_elements` | Trap, as for memory |
| Instances, tables, memories per Store | 16, 8, 4 (fixed) | Instantiation fails with `host.engine-error` |
| Linear memory total over all Stores of the process | `session_memory_mib` | The new instance is refused with `session.memory-exceeded`. Not counted as a failure (reason `host-capacity`) |

The `ResourceLimiter` MUST trap on growth failure (`trap_on_grow_failure(true)`), so a guest never observes a failed growth as `-1`. The same rule applies to table growth past the table limit. The Store data record has this layout:

```rust
// ilium-plugin-host/src/store_data.rs (illustration of the contract)
pub struct StoreData {
    pub plugin: PluginId,
    pub side: Side,                  // Server, Client or Scene
    pub instance: u64,               // rises for each new instance of this plugin side
    pub kind: InstanceKind,          // Main or Job { job_id }
    pub authorization_epoch: u64,    // grant generation this instance was linked against
    pub quota: QuotaHandle,          // execution quota group handle
    pub call: Option<CallState>,     // class, start time, deadline, soft flag, late flag
    pub limits: StoreLimits,
    pub wasi: WasiCtx,               // see the WASI section
    pub resources: ResourceTable,
}
```

- **[HST-074]** Every Store MUST be created with `StoreLimits` taken from the clamped manifest limits and MUST have `trap_on_grow_failure(true)`.
- **[HST-075]** Each Store MUST carry the plugin id, side, instance number, kind, authorization epoch and quota handle, and every import MUST check the authorization epoch against the current grant generation before it acts. A mismatch returns `revoked`.

## WASI policy

Rust components built for `wasm32-wasip2` and TypeScript components built by `componentize-js` import parts of WASI Preview 2. The host links `wasmtime-wasi` Preview 2 with these rules.

| WASI interface | Policy |
|---|---|
| `wasi:cli/stdout`, `wasi:cli/stderr` | Captured line by line into the plugin log at level `info` (stdout) and `warn` (stderr). A line longer than 16 KiB is cut and marked `[cut]`. The `log_lines_per_second` limit applies |
| `wasi:cli/stdin` | Always empty |
| `wasi:cli/environment` | No variables; one argument, the plugin id |
| `wasi:cli/exit` | A call traps with `wasi.exit` |
| `wasi:clocks`, `wasi:random` | Allowed. Wall-clock time is the real clock; monotonic time is the host monotonic clock; random bytes come from the operating system |
| `wasi:io` | Allowed |
| `wasi:filesystem` | Linked, but with preopens only for scopes that an `fs.*` grant makes available, mapped through `ilium-platform` secure file access. With no `fs.*` grant the preopen list is empty |
| `wasi:sockets` | Refused. A component that imports it is refused at load with `component.wasi-forbidden` |
| `wasi:http` | Refused in the same way. HTTP goes only through the `http` capability, which applies allowlists, size caps and the outbound-request rules |

Package-time composition with `wasi-virt` is a supported alternative for a plugin author who wants a smaller import set. It does not change the host rules.

- **[HST-076]** The host MUST link WASI Preview 2 with captured stdout and stderr, an empty environment, no stdin, `wasi:cli/exit` as a trap, and preopens only from `fs.*` grants.
- **[HST-077]** A component that imports `wasi:sockets` or `wasi:http` MUST be refused at load with `component.wasi-forbidden` and MUST NOT be instantiated.
- **[HST-078]** A stdout or stderr line longer than 16 KiB MUST be cut at 16 KiB and marked `[cut]`.

## Epoch ticker and deadlines

Wasmtime's **epoch interruption** lets the host stop guest code without a per-instruction counter. The Engine has one counter, the epoch. A ticker thread increases it at a fixed period. Each Store can ask to be interrupted when the counter reaches a value.

- **[HST-079]** Each Engine MUST have exactly one epoch ticker thread, named `ilium-plugin-epoch`, that increases the epoch every 10 ms. The tick period is 10 ms on every platform.
- **[HST-080]** Before every guest call the host MUST install an `epoch_deadline_callback` for the Store. The callback runs on each tick while that call is executing. It compares the host monotonic clock with the call's deadlines and returns one of: continue, yield (only for yielding call classes), or a trap.
- **[HST-081]** The host MUST set the instance deadline of a call with deadline `d` milliseconds to `ceil(d / 10) + 1` ticks after the call starts. A guest that spins traps no earlier than `d` and no later than `d + 20` ms of wall time on a host that is not overloaded, and a call that returns at `d - 1` ms never traps. A 20 ms deadline traps between 20 and 40 ms.
- **[HST-082]** The ticker MUST continue while any call is in flight, and MUST detect a clock jump of more than one second between two ticks (for example after a system suspend) and in that case skip deadline decisions for that tick.

Two kinds of deadline exist. A **hard** deadline traps the instance when it fires. A **soft** deadline marks the call late: the host continues the call, discards its result, and traps only if a grace period of 100 ms past the soft deadline also expires. The call classes that are hard or soft, and the effect of a breach for each, are the single table in [Scheduling, deadlines and cancellation](/pages/reference-host-scheduling/).

- Only the call classes marked "yields" return `yield` from the callback: `activate`, job runs and long service calls. Their wall time still counts against the deadline. All other classes run to completion or to the deadline without yielding.
- A guest call that is waiting in a synchronous host import does not execute guest code, so no tick can trap it during the import. The trap fires on the first epoch check after the import returns. Time spent in such an import counts toward the deadline.
- Time that the host spends after a call has returned (applying the returned submissions, delivering later events) does not count toward the deadline of that call.

- **[HST-083]** A trap caused by an epoch deadline MUST carry the error `trap.deadline` with the call class and the limit in milliseconds, and MUST be logged once.

## Component validation at install

The host validates a component when a package is installed and again when the package is loaded. T2 and T3 validation runs inside the helper, because parsing is done by `Component::new` there.

1. The bytes are a valid component (`wasmparser` validation with the features of the Config). Failure: `package.component-invalid`.
2. The component size is at most 32 MiB. Failure: `component.too-large`.
3. The component targets the world named in the manifest (`world`) of the right side. Failure: `component.world-mismatch`.
4. The export set equals the required exports of the world plus the optional exports listed in the manifest. Failure: `manifest.exports-mismatch`.
5. The custom section `ilium:api-version` exists and holds three big-endian unsigned 16-bit integers (major, minor, patch) equal to the manifest `api`. For contract version one the bytes are `00 00 00 01 00 00`. Failure: `package.api-section-missing` when the section is absent, `manifest.api-version` when it differs from the manifest.
6. No single custom section is larger than 4 MiB and the custom sections together are at most 8 MiB. The `name` section MAY be stripped by `ilium plugin build --release`. Failure: `component.custom-section-too-large`.
7. Every import is an interface that the host can link under the rules above. Failures: `manifest.import-not-requested`, `component.wasi-forbidden`, or `component.import-unknown` for an interface that does not exist in `ilium:plugin@0.1.0`.

- **[HST-084]** The host MUST apply the seven validation steps in this order and MUST report the first failing step's error id.
- **[HST-085]** The `ilium:api-version` custom section MUST be exactly six bytes and MUST equal the manifest `api` in all three fields.
- **[HST-086]** A component larger than 32 MiB, a custom section larger than 4 MiB, or custom sections together larger than 8 MiB MUST be refused.

## Cargo and build notes for host implementers

The host crate compiles through ni-build on ni-vm like every crate of the workspace (see the project instructions). The release build step that produces `.cwasm` files is a build-script-free tool, `ilium-plugin-precompile`, that links the same `Config` function as the host (`runtime_config()` in `ilium-plugin-host`) so the two cannot drift. The step writes `<artifact>.cwasm` and a header with the config fingerprint (HST-057).

```rust
// ilium-plugin-host/src/runtime_config.rs (illustration of the contract)
pub fn runtime_config() -> wasmtime::Config {
    let mut config = wasmtime::Config::new();
    config
        .wasm_component_model(true)
        .wasm_component_model_async(false)
        .epoch_interruption(true)
        .consume_fuel(false)
        .max_wasm_stack(512 * 1024)
        .async_stack_size(1024 * 1024)
        .signals_based_traps(true)
        .parallel_compilation(true)
        .wasm_simd(true)
        .wasm_relaxed_simd(false)
        .wasm_threads(false)
        .wasm_multi_memory(false)
        .wasm_memory64(false)
        .wasm_gc(false)
        .generate_address_map(true)
        .wasm_backtrace(true);
    config
}
```

- **[HST-087]** The precompile step and the host MUST obtain their `Config` from the same function.

## Errors and edge cases

| Situation | Result | Id |
|---|---|---|
| A `.cwasm` was built by another Wasmtime version or another `Config` | `Component::deserialize` is not attempted when the fingerprint differs. The host loads the embedded `.wasm` with `Component::new` instead and logs a warning. A release build MUST have zero such fallbacks, and a CI test enforces it | `host.cwasm-incompatible` |
| Embedded `.cwasm` has no embedded `.wasm` to fall back to | The plugin is disabled and the build is considered broken | `host.cwasm-incompatible` |
| Package contains a `.cwasm` | Install refused | `package.precompiled-forbidden` |
| Component imports `wasi:sockets` or `wasi:http` | Refused | `component.wasi-forbidden` |
| Component imports an interface the manifest never requested | Refused at install or load | `manifest.import-not-requested` |
| Function of an unrequested capability called | The instance traps | `host.capability-not-requested` |
| Epoch deadline | The instance traps (hard) or the call is marked late (soft) | `trap.deadline` |
| Guest memory growth refused | Trap; log line `memory limit <N> MiB reached` | none |
| Stack overflow | The instance traps | `host.stack-overflow` |
| Wasmtime internal compile error | Load fails; plugin not activated | `host.engine-error` |
| Component uses `wasm_component_model_async` | Refused | `component.invalid` |
| Compile cache unavailable | Compile in memory, log once | `host.cache-unavailable` |
| System clock jumps during a call | No deadline decision on the jump tick | none |
| API version section missing | Refused | `package.api-section-missing` |
| API version section wrong | Refused | `manifest.api-version` |

- **[HST-088]** When the config fingerprint of an embedded `.cwasm` differs from the host's, the host MUST NOT call `Component::deserialize` on it, MUST fall back to `Component::new` on the embedded `.wasm`, and MUST log `host.cwasm-incompatible`. A release-build test MUST fail if any bundled plugin takes this path.
- **[HST-089]** A stack overflow in guest code MUST trap the instance with `host.stack-overflow` and MUST NOT crash the process.
