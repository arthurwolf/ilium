## Requirements for the host API

Normative behaviour of host functions: the error record, traps, the restart and disable rule, limits, clamps, quotas and install reporting. Contract version: ilium:plugin@0.1.0.

The rows follow the format and the observation channels of the [requirements index](/pages/reference-requirements/). The id prefix is `API`.

| Id | Requirement | Source | Observable test |
|---|---|---|---|
| [API-001] | A fallible host function MUST return result<T, plugin-error>. The record MUST carry code, message and an optional retry-after-ms. | [the plugin error record](/pages/reference-errors-and-limits/#the-plugin-error-record) | (sync-return) call any fallible function with a bad argument -> the result is err with the three fields. |
| [API-002] | The error code MUST be one of the 15 codes: not-permitted, not-found, invalid-argument, conflict, quota-exceeded, rate-limited, busy, timed-out, cancelled, unsupported, pane-not-ready, revoked, io, network, internal. | [the plugin error record](/pages/reference-errors-and-limits/#the-plugin-error-record) | (sync-return) provoke each documented failure -> the code is in the list of 15 and no other value appears. |
| [API-003] | retry-after-ms MUST be set for rate-limited and for quota-exceeded caused by the CPU budget. A plugin MUST NOT match on message text. | [the plugin error record](/pages/reference-errors-and-limits/#the-plugin-error-record) | (sync-return) exceed the toast rate -> rate-limited with retry-after-ms greater than 0. |
| [API-004] | Every function that returns a result MAY return not-permitted, revoked and internal. A function that returns a request-id MAY also return busy. | [the plugin error record](/pages/reference-errors-and-limits/#the-plugin-error-record) | (sync-return) call a request-id function with 4,097 requests pending in the session -> err busy. |
| [API-005] | For a call that returns a request-id, grant, scope, syntax and per-call cap checks MUST fail in the call. Disk, network, process and user failures MUST arrive in the completion as failed(code). | [the plugin error record](/pages/reference-errors-and-limits/#the-plugin-error-record) | (sync-return) fs read of a path outside the scope -> err at once. (completion) read of a file that vanished -> failed(not-found). |
| [API-010] | Calling an import whose capability the manifest never requested MUST trap. | [traps](/pages/reference-errors-and-limits/#traps) | (trap) call an import without its grant in the manifest -> the instance traps and the log names the interface and function. |
| [API-011] | An invalid ui-tree MUST trap: an index out of range, a graph that is not a tree, a duplicate key in one tree, more nodes than the effective ui_tree_nodes limit, or a layout whose child count differs from its constraint count. | [traps](/pages/reference-errors-and-limits/#traps) | (trap) return a tree with 4,097 nodes at the default limit -> trap. |
| [API-012] | A hard deadline breach in `activate`, `on-events` or `views.render` MUST trap. A breach in `deactivate` MUST drop the instance without a trap and keep no restore bytes. | [traps](/pages/reference-errors-and-limits/#traps) | (trap) sleep 100 ms inside on-events at the 20 ms deadline -> trap and a log line "on-events 100 ms (limit 20 ms)". |
| [API-013] | Exceeding the linear memory or table limit MUST trap. | [traps](/pages/reference-errors-and-limits/#traps) | (trap) allocate past memory_mib -> trap. |
| [API-014] | A Rust panic or an uncaught TypeScript exception in an export MUST trap. | [traps](/pages/reference-errors-and-limits/#traps) | (trap) panic in on-events -> trap. |
| [API-015] | A trap MUST end the instance. The plugin MUST be restarted under the restart rule. A plugin MUST NOT be able to catch a trap. | [traps](/pages/reference-errors-and-limits/#traps) | (restart-schedule) trap once -> new instance after 1 s. |
| [API-016] | Every not-permitted result and every trap MUST be logged with the plugin id, the interface and the function. | [traps](/pages/reference-errors-and-limits/#traps) | (log-line) call a function without its grant -> one log line with the three fields. |
| [API-040] | The restart rule MUST apply per plugin and per side. The first failure in a 10-minute window restarts after 1 s. The second restarts after 5 s. The third disables the plugin on that side. No 30 s step exists. A failure older than 10 minutes MUST NOT count. | [restart and disable rule](/pages/reference-errors-and-limits/#restart-and-disable-rule) | (restart-schedule) failures at 0, 2 and 4 minutes -> restart after 1 s, restart after 5 s, disabled. Failures at 0 and 11 minutes -> both restart after 1 s. |
| [API-041] | A disabled side MUST stay disabled until a manual enable. A manual enable MUST reset the failure count to zero. A successful run MUST NOT clear a failure sooner. | [restart and disable rule](/pages/reference-errors-and-limits/#restart-and-disable-rule) | (restart-schedule) disable, enable in Settings, fail once -> restart after 1 s. |
| [API-042] | A trap, a deadline breach and an activate call that returns an error MUST count as failures. A revoked re-activation, a disable, an upgrade, a shutdown and a failed job MUST NOT count. | [restart and disable rule](/pages/reference-errors-and-limits/#restart-and-disable-rule) | (restart-schedule) revoke a grant three times in a minute -> re-activated each time, never disabled. |
| [API-043] | A manifest limit above the tier ceiling MUST be clamped and logged. The install MUST NOT fail for it. | [resource limits in the manifest](/pages/reference-errors-and-limits/#resource-limits-in-the-manifest) | (install-error) request http_streams 99 as T2 -> install succeeds. (log-line) a clamp line names the key and 4. |
| [API-044] | A failing view MUST count against the plugin and not against the view alone. | [restart and disable rule](/pages/reference-errors-and-limits/#restart-and-disable-rule) | (restart-schedule) trap in views.render -> the plugin restarts, not only the view. |
| [API-045] | A scene failure MUST count as a failure of the whole plugin on that side. | [edge cases and errors](/pages/api-scenes/#edge-cases-and-errors) | (restart-schedule) trap in a scene frame -> the client side restarts after 1 s. |
| [API-046] | When the memory budget of the session is reached, a new instance MUST be refused and logged. The refusal MUST NOT count as a failure. The side MUST stay inactive with the reason host-capacity. | [edge cases](/pages/reference-errors-and-limits/#edge-cases) | (log-line) activate beyond 1,024 MiB total -> refusal logged, state inactive, failure count unchanged. |
| [API-060] | Truncations and clamps MUST be only those in the exception table. Every other over-limit call MUST return an error and MUST NOT cut silently. | [requestable limits](/pages/reference-errors-and-limits/#requestable-limits) | (sync-return) pass a 65 KiB raw input -> err invalid-argument and no bytes sent. |
| [API-061] | A cap that depends on held or cumulative state MUST return quota-exceeded. A cap the plugin can check in advance MUST return invalid-argument. | [requestable limits](/pages/reference-errors-and-limits/#requestable-limits) | (sync-return) fs.scan over 65,536 entries -> failed(quota-exceeded). send-input with 17 stages -> invalid-argument. |
| [API-062] | A call over a fixed cap such as 1 MiB for a synchronous fs.read, 8 MiB per HTTP request, or a timer interval under 50 ms MUST return invalid-argument. | [requestable limits](/pages/reference-errors-and-limits/#requestable-limits) | (sync-return) set a timer of 10 ms -> err invalid-argument. |
| [API-070] | Session-wide limits MUST count across all plugins of the session: 64 HTTP streams, 16 children, 4,096 pending requests, 65,536 decorations, 32 key grabs. | [requestable limits](/pages/reference-errors-and-limits/#requestable-limits) | (sync-return) two plugins open 32 streams each, one opens a 65th -> quota-exceeded. |
| [API-071] | Rate rules MUST be enforced per plugin as listed: toast 3 per 10 s, geocode 1 per second, notify 6 per minute, open-external 10 per minute, play-sound 4 per second, topics.publish 100 per second, journal.log-event 20 per second, send-input 20 per second per pane. Each rate MUST be a sliding window; a refused operation MUST NOT enter the window; and the refusal MUST carry `retry-after-ms` until the oldest counted operation leaves the window. | [requestable limits](/pages/reference-errors-and-limits/#requestable-limits) | (sync-return) call notify 7 times in one minute -> the 7th returns rate-limited; call notify 6 times at second 55 and once at second 65 -> the call at second 65 is refused. |
| [API-072] | The execution quota group MUST be a token bucket of 2,000 ms of CPU time refilling at 500 ms per second. The bucket is empty at a balance of 0 or less, and the balance MAY go negative. An empty bucket MUST make submissions and request-id calls return quota-exceeded with retry-after-ms = max(100, ceil_10(-balance_ms * 2)). | [requestable limits](/pages/reference-errors-and-limits/#requestable-limits) | (sync-return) spend 2,150 ms CPU in jobs from a full bucket (balance -150 ms), then submit -> quota-exceeded with retry-after-ms 300; drive the balance to -100 ms, submit -> retry-after-ms 200. |
| [API-073] | Pending requests MUST be limited to 64 per plugin by default. A request MUST count from the return of its id to the enqueue of its completion; refused submissions and synchronous calls MUST NOT count. A further call MUST return busy. | [Reference summary](/pages/reference/#quick-lookup) | (sync-return) start 65 slow calls -> the 65th returns busy. |
| [API-074] | A timer MUST NOT fire inside the call that set it; the first timer-fired MUST be queued after the delay counted from the return of timers.set; timers.cancel MUST remove a queued, undelivered timer-fired of that timer; cancelling an unknown id MUST be a silent no-op. | [clock and timers](/pages/api-clock-and-timers/#rules) | (event-delivery) set a 50 ms timer, cancel it at 40 ms with a queued tick -> no timer-fired is delivered. |
| [API-080] | The install MUST stop at the first failing step and MUST report every failure found inside that step, in the documented order. The exit code MUST be 1 when any error line was printed. | [install checks and error codes](/pages/reference-manifest/#validation-and-error-model) | (install-error) a package with a bad id and an unknown key -> only the id code. A package with two unknown keys -> both codes. |
| [API-081] | A trap MUST carry exactly one of the seven trap codes `trap.deadline`, `trap.memory`, `trap.table`, `trap.submission-batch`, `trap.invalid-ui-tree`, `trap.abi` and `trap.panic`, or, for the three host-side faults, `host.capability-not-requested` (a call of a never-requested capability), `host.import-panic` (a panic in a host import) or `host.stack-overflow` (a stack overflow in guest code), and the log line of the trap MUST name it. | [trap codes](/pages/reference-errors-and-limits/#trap-codes) | provoke each trap and read the code in `ilium plugin logs` |
| [API-082] | An SDK item that a release marks for removal MUST carry the Rust `#[deprecated(since = "<sdk version>", note = "...")]` attribute or the TypeScript `@deprecated` JSDoc tag in that same release, on the item itself. The note MUST name the successor and the removal minor. A changelog entry alone MUST NOT mark an item. | [SDK deprecation](/pages/reference-sdk-deprecation/) | Doc check in ilium/tests/plugin_user_flows: a Rust item and a TypeScript export marked in a fixture SDK each carry the mark with a successor and a removal minor. |
| [API-083] | A deprecated SDK item MUST keep its signature and its behaviour until the removal minor named in its mark. A patch release MUST NOT remove it, and a minor release MUST NOT remove it before two minors after the release that marked it. | [SDK deprecation](/pages/reference-sdk-deprecation/) | Doc check in ilium/tests/plugin_user_flows: the removal rule of the SDK deprecation page matches the minor and patch rules in the versioning policy of the SDK pages. |
| [API-084] | Each SDK release MUST list every item it marks under a `Deprecated` heading of its changelog entry, and every item it removes under a `Removed` heading, each entry naming the item, its successor and its removal minor. | [SDK deprecation](/pages/reference-sdk-deprecation/) | Doc check in ilium/tests/plugin_user_flows: the changelog example on the SDK deprecation page has both headings and names all three fields. |
| [API-085] | A release that marks an SDK item MUST already ship its successor, so that an author can move in the same release. An item with no successor MUST say so in its note instead. | [SDK deprecation](/pages/reference-sdk-deprecation/) | Doc check: each marked fixture item names a successor that exists in the same fixture release, or says it has none. |
| [API-086] | The release that removes an SDK item MUST be the minor named in its mark, MUST NOT be a patch release, and MUST NOT change the signature or behaviour of any other item. | [SDK deprecation](/pages/reference-sdk-deprecation/) | Doc check: the removal rule of the SDK deprecation page names the minor of the mark and excludes patch releases. |
| [API-087] | The host MUST NOT write a `deprecated` record, a log line or a refusal for an SDK deprecation. | [SDK deprecation](/pages/reference-sdk-deprecation/) | Load a plugin built with a deprecated SDK item and check that `ilium plugin logs` has no `deprecated` record. |
| [API-088] | A plugin MUST treat an error code it does not know as a failed call of unspecified cause and MUST NOT trap or match on `message`. The SDKs MUST expose such a code as an `Unknown` variant that carries the code string, and a code added in a later contract version MUST be a minor change of the contract that does not break a plugin built for an earlier minor. | [reference errors and limits](/pages/reference-errors-and-limits/#error-code-extensibility-and-retry-hints) | (sync-return) call a host function against a fixture host that returns an invented code -> the Rust SDK yields `ErrorCode::Unknown("<code>")`, the TypeScript SDK a string, and the plugin keeps running. |
| [API-089] | A plugin that gets `retry-after-ms` MUST NOT repeat the same call before that many milliseconds have passed and SHOULD add random jitter of up to 20 percent. The host MUST NOT trap or penalise an early retry, MUST answer it with the same error and MUST NOT shorten or extend the original hint because of it. Refused attempts MUST NOT enter the rate window or charge CPU time to the quota group beyond the cost of the call itself. | [reference errors and limits](/pages/reference-errors-and-limits/#error-code-extensibility-and-retry-hints) | (sync-return) trigger `rate-limited` with a hint of 500 ms, retry at 100 ms -> the second call returns `rate-limited` again, no trap, and the window counts only the first allowed operations. |
| [API-090] | When a plugin instance traps, restarts or is replaced by an upgrade, the host MUST cancel every pending request of the old instance, MUST reclaim its pending slots and held results, and MUST drop a late completion of such a request instead of delivering it to the new instance. The new instance MUST NOT see a `request-completed` event for an id it did not issue, and `take-*` of an old id MUST return `none`. | [requests and outcomes](/pages/requests-and-outcomes/#stale-completions-and-pending-request-lifetime) | (event-delivery) start a slow call, force a trap, let the host complete the call late -> the restarted instance gets no completion, and `pending_requests` is 0. |
| [API-091] | A pending request MUST have a host-side lifetime limit of 120 seconds by default from the return of its id. On expiry the host MUST complete it with the outcome `cancelled`, free the pending slot and remove any held result. The same limit MUST apply if the completing worker is lost. | [requests and outcomes](/pages/requests-and-outcomes/#stale-completions-and-pending-request-lifetime) | (event-delivery) start a call whose backend never answers -> after 120 s the plugin gets `cancelled` and the 65th call no longer returns `busy`. |
| [API-092] | The host MUST keep a per-plugin, per-side counter for each trap code of [API-081] and for each restart, MUST collapse identical consecutive log lines of one trap code within 10 seconds into one line with a repeat count, and MUST retain a crash record (trap code, time, side and the last 20 log lines) for each plugin disabled by the restart rule until the plugin is enabled again or removed. `ilium plugin logs` MUST show the crash record. | [reference host telemetry](/pages/reference-host-telemetry/#operator-observability-of-traps) | (install-error) trap one plugin three times in 10 minutes -> the counters read 3, the logs show one collapsed line when the traps repeat within 10 s, and the crash record is still shown after the disable. |
| [API-093] | The host MUST offer `ilium plugin enable <id>` and an administrator bulk form for every disabled plugin, MUST show the crash record of [API-092] before it enables, and MUST clear the restart window on an enable so that the 10-minute count starts again at zero. An enable MUST NOT clear the crash record before the plugin has run for 10 minutes without a trap. | [guide admin failure runbook](/pages/guide-admin-failure-runbook/#recover-a-disabled-side) | (install-error) disable a plugin by three traps, enable it, trap once -> the plugin restarts and is not disabled; the crash record survives until 10 minutes of clean running. |
| [API-094] | A host release MUST NOT lower a tier ceiling, a rate rule or a session-wide limit of [API-043], [API-070] or [API-071] below the value a plugin was admitted with within the same contract minor. A change MUST be listed in the release notes, and a plugin MUST be able to read its effective limits at runtime from the `limits` record of the host info, which names each limit, its value and its source (default, manifest or user). | [reference host aggregate limits](/pages/reference-host-aggregate-limits/#limit-changes-between-host-releases) | (sync-return) read the `limits` record -> each documented limit appears with its effective value and source; a fixture upgrade that lowers one inside the same minor is refused by the doc check. |
| [API-095] | A side refused for memory MUST be queued in the order of refusal and admitted first-in first-out when capacity frees, one admission per plugin at a time. The host MUST retry admission whenever an instance ends and at least every 30 seconds, MUST NOT let one plugin take two slots while another waits, and MUST show a notice to the user that names the plugin and says the side is inactive for lack of memory, until it is admitted or removed. | [reference host scheduling](/pages/reference-host-scheduling/#re-admission-after-a-memory-budget-refusal) | (event-delivery) fill the budget, request two more sides, free one instance -> the earlier refused side starts first and the notice is shown until it does. |
| [API-096] | The host MUST offer a generic `cancel(request-id)` import that, for a pending request of the calling plugin, stops the underlying work, frees the pending slot at once and completes the request with outcome `cancelled`; for an unknown, foreign or already completed id it MUST return `not-found` without effect, and repeated calls MUST be idempotent. | [Cancelling a pending request](/pages/requests-and-outcomes/) | Cancel a pending request; check the work stops and the outcome is cancelled; cancel an unknown id and check not-found with no effect. |
| [API-097] | For every host function that returns a request id, the reference MUST state whether a retry after a timeout or failure is idempotent and whether its effect is `none` or `unknown`; the host MUST NOT apply a retried call twice when it carries the same dedup key within its 128-character key scope. | [Retry semantics of host calls](/pages/reference-errors-and-limits/) | Retry a timed-out call that carries a dedup key; check the effect is applied once and the reference lists its effect class. |
| [API-200] | Every effectful import MUST be rate limited per plugin by a named token bucket, and the call that finds the bucket empty MUST return `err(busy)` with reason `rate-limited` and a `retry-after-ms` value of at least 1. | [reference-errors-and-limits](/pages/reference-errors-and-limits/) | unit test planned, red until implemented |
| [API-201] | A subscribe import MUST be idempotent per (plugin, topic, filter): a second identical subscribe MUST return the same subscription id and MUST NOT duplicate delivery, and unsubscribe of a stale id MUST return ok. | [api-events](/pages/api-events/) | unit test planned, red until implemented |
| [API-203] | A write import MUST either apply completely or not at all for payloads up to 4 MiB, and an interrupted write MUST leave the previous content intact, and the result MUST carry the new content hash. | [api-fs](/pages/api-fs/) | unit test planned, red until implemented |
| [API-204] | Every stream import MUST define a maximum chunk of 64 KiB (proposed, owner to confirm), a maximum of 8 unread chunks, and on overflow the host MUST pause the producer and MUST NOT drop data; a stream closed by either side MUST deliver exactly one `stream-closed` event with a reason code. | [api-http-streams](/pages/api-http-streams/) | unit test planned, red until implemented |
| [API-209] | A service call chain deeper than 4 hops, or a cycle where a plugin is already on the chain, MUST be refused with `reentrant` before any callee runs. | [api-services](/pages/api-services/) | unit test planned, red until implemented |
| [API-213] | A settings write MUST validate against the declared schema before storing, MUST return `invalid-argument` with the JSON pointer of the first failing field, and MUST emit one `settings-changed` event only after the value is persisted. | [api-settings](/pages/api-settings/) | unit test planned, red until implemented |
| [API-214] | Registering a command id that another plugin already owns MUST return `conflict` and leave both registrations unchanged, and unregistering a command during its own invocation MUST let that invocation finish. | [api-commands](/pages/api-commands/) | register the same id from two plugins and assert `conflict` with both registrations unchanged; unregister a command inside its own handler and assert that the handler completes and its result is delivered. |
| [API-216] | An import that targets a pane closed before the host applied it MUST complete as `refused(not-found)` and MUST NOT affect the pane that reuses the screen position. | [api-pane-lifecycle](/pages/api-pane-lifecycle/) | unit test planned, red until implemented |
